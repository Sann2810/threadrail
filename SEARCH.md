# Meaning-based thread search — ThreadRail 1.6.10

Implemented: a persistent magnifying glass beside Top's position, a search panel, and Alt+Shift+F to open it even when the rail is hidden. Search is scoped to the current conversation, independently of the ten-exchange navigation window. Both user inputs and assistant outputs are searched. Results show original excerpts and jump to the matching passage. Word-result jumps target the highlighted word, not the surrounding display excerpt. All distinct query words are shown as vertical rows with counts, including function words. Each row expands and collapses its own results. Indexing and final ranking have separate loading labels, and preliminary matches remain usable while ranking finishes. No answer generation or external AI service is involved.

## Retrieval pipeline

1. The existing provider adapter extracts clean text and stable exchange IDs. Each captured source retains its role, original question, stable message identity, text version and paragraph offsets. Text survives host virtualization; only the current window holds live DOM bindings. Result caches and hidden result rows do not retain detached transcript subtrees.
2. Whole-message windows of 140 words with 28-word overlap remain available for context, tables and code. Sentence and clause candidates also preserve each original substring and its offset. Independent events within a short sentence can therefore rank separately; passage extraction is shared across live messages and saved chats. Long outputs also retain paragraph candidates as offsets in canonical text, deduplicated against identical sentence ranges.
3. BM25-style lexical scoring preserves exact words and identifiers. Each passage is embedded on its own. Original input context remains available for name disambiguation, but prompt instructions no longer enter answer embeddings. No query-specific synonyms, invented event descriptions or answer generation are used.
4. Retrieval combines cosine similarity (90%) with normalized lexical scoring (10%), weighted by meaningful-query coverage. Message-level term frequencies keep longer or more fragmented messages from redefining rarity. Numbers, code identifiers and likely inline proper names can act as rare anchors; arbitrary rare ordinary words cannot. This remains a lightweight heuristic rather than full named-entity recognition.
5. In-thread search first embeds overlapping windows over the entire captured history. It compares the twelve strongest windows with the query, refines the top four plus the two dense leaders and up to two high-coverage lexical windows, then computes missing sentence/clause vectors only within those windows. Small or nearly complete indexes finish their remaining fine vectors directly and skip window ranking; fully warm indexes use the original single ranking pass. Large cold indexes use bounded candidate retrieval, not an exhaustive semantic comparison of every sentence. The BGE model uses a model-specific cosine floor of .58; this scale differs from the old MiniLM model. In semantic mode, lexical evidence can independently qualify a result only when it covers at least half the meaningful query terms. A single incidental overlap no longer bypasses the semantic floor. Up to 24 diverse candidates are compared with the query by a packaged MS MARCO cross-encoder. Its relative softmax scores contribute 20% of the final ranking, with the original retrieval score contributing 80%. Close pair scores leave retrieval in control; clear differences help separate an actual remembered input from advice about a related topic. These are ranking signals, not confidence probabilities. The smart column initially shows two results, with Show more revealing up to six, deduplicated per exchange. Excerpts include surrounding source context while jumps retain the precise passage offsets.
6. Beside smart matches, a separate word index groups every matching whole message by query word. Matching uses Unicode word boundaries, case folding and NFKC normalization. Word lookup includes function words; semantic scoring still filters them. A conservative ASCII English family key groups regular plural and “-ing” forms, including doubled consonants. It is not a full lemmatizer and does not expand synonyms or arbitrary substrings. The index keeps the earliest actual matching token per whole source message, so variants do not duplicate messages or replace source offsets. Each group follows conversation order across both roles. Semantic chunks and paragraph candidates cannot duplicate a whole message in the word index. Each message appears once per tag, even if it also appears among best matches or under another tag. The snippet highlights its first occurrence and jumps to that passage. There is no similarity threshold or total-result cap here: each word starts collapsed and initially shows two rows when expanded; **Show more** adds up to 20 at a time, and switching tags retains that word’s expanded list.
7. Selecting a result first materializes its turn, then locates the excerpt using a DOM Range and moves to that passage. Gemini collapsed prompts expand through the host control before alignment. For a saved message outside the DOM, the existing bounded history scan reloads the original source and verifies identity and text before navigation. Edits invalidate old text; unavailable or cancelled scans report failure instead of jumping to a nearby result.

The browser models are pinned quantized ONNX conversions of [BGE-small-en-v1.5](https://huggingface.co/BAAI/bge-small-en-v1.5), a 384-dimensional retrieval encoder, and [MS MARCO MiniLM](https://huggingface.co/Xenova/ms-marco-MiniLM-L-6-v2), a query/passage cross-encoder. BGE uses normalized CLS pooling and its author's retrieval instruction on queries only. The inference limit here is 256 wordpieces. These are primarily English models; multilingual, highly ambiguous, negated and pronoun-heavy queries remain incompletely evaluated. The separate native Claude mod retains its existing MiniLM runtime.

## Local execution and performance

Transformers.js 4.3.1 and ONNX Runtime execute in the extension service worker. The synthetic demo uses a dedicated worker. The JavaScript runtime, WASM binary, tokenizer, and model weights are bundled; runtime inference does not download executable code or contact a model host. The WASM factory is embedded in the JavaScript bundle, avoiding dynamic module imports in the service worker. This follows the runtime separation described in [Hugging Face's extension architecture guide](https://huggingface.co/blog/transformersjs-chrome-extension); [Chrome's extension CSP](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy) permits packaged WebAssembly with `wasm-unsafe-eval`.

Window indexing begins after a short quiet interval while the chat is open. Batches group similarly sized inputs, avoid repeated inference for identical text, and reuse compatible vectors across remounts, tab reloads and browser restarts. Query and ranking jobs take priority over queued background work. Sentence/clause refinement runs only for a query's candidate windows; closing the panel does not throw away accepted vectors. Exact-word matches are immediately available independently of the models.

A fixed replay of 31,736 characters from an eight-exchange Gemini conversation took 227.6 seconds to first completed ranking on 1.6.5, versus 50.8 seconds with the new two-stage pipeline, and 2.9 seconds after reload with the saved cache. These are one-machine isolated-browser measurements, not a device-wide benchmark or a claim that initial indexing is instant. The first model load and first read of a large unseen history still take time. The same original handoff query returned the relevant passage first. The full regression suite separately checks ranking and exact destinations.

Captured text and compatible passage vectors share the existing extension-owned local library. There are no model host requests, search server, API key, or external inference calls. Private browsing and unsaved temporary routes do not persist conversation caches. Library Remove and Clear also invalidate retained text in open tabs and guard against delayed writes restoring it. Pausing automatic saving keeps subsequent page-local history in memory until the tab closes. A model failure produces an explicitly labeled word-search fallback.

## Coverage and older history

Only text the host has exposed can be captured. Once captured, both inputs and outputs stay searchable after their DOM window unloads; saved local history can also be restored in the same thread after a browser restart. Word groups include loaded and retained messages once each, in captured conversation order. Stable host IDs, public message ordinals, overlapping windows and prompt context preserve identities; indistinguishable fallback identities without those signals remain a limitation. Loaded edits update the stored message and invalidate affected vectors.

Coverage distinguishes loaded exchanges and saved messages and remains partial. It does not promise unvisited account history or a complete conversation export. **Load earlier** is conditional on public earlier-history evidence, independently of whether query ranking has finished. Capturing the known beginning suppresses the action even when those messages later unload. Unknown history and disabled or transcript-quoted controls do not produce the action. Native control availability changes update the UI. Loading uses exposed older-message buttons and the host's ordinary scroll interface and retains the newly seen text even when restoring the reading position unloads it. Selecting a retained result follows public message boundaries and Load later controls for up to 45 seconds, revalidates the original source, then uses the same exact passage jump. The scan shows a persistent Cancel action; unavailable targets offer Retry and restore the reading position. Escape, wheel or pointer input cancels the scan. No undocumented chat APIs are used.

## Reproducible assets

Run `npm run prepare:model` once before building. It verifies pinned revisions and SHA-256 values against `retrieval-model-files.json` (browser BGE), `reranker-files.json` (local cross-encoder), and `model-files.json` (native Claude mod MiniLM). Only development preparation contacts Hugging Face. The browser build packages the retrieval and ranking models with their licenses; unused experiments and the native-only model are excluded. Cached vectors require both an identical embedding-text fingerprint and the same model/pooling/query-format version, so old MiniLM library vectors are rebuilt locally.

Technical meaning hints identify JavaScript runtimes such as a Node toolchain, without adding those hints to excerpts or word tags. A substantive event followed by a temporal background clause is encoded both as the complete query and its leading event, with weights 25% and 75%, then normalized. Short prefixes and questions about temporal order keep the full query. This is a local retrieval heuristic, not language-model reasoning.

## Cross-conversation retrieval (1.5.0)

The All chats extension page builds a shared index from locally captured messages across websites. Durable host message IDs update existing records; otherwise text fingerprints and adjacent answer context identify sources. Overlapping virtualized windows merge around shared anchors, retaining captured offscreen text. Ambiguous identity and edits without native IDs can preserve historical copies; coverage is explicitly marked partial and the local library is user-managed.

Library ranking weighs semantic similarity at 90% and lexical score at 10%, with lexical evidence weighted by meaningful-query coverage. This prevents a short prompt containing only a character's name from dominating a query about that character's behavior. The existing rare-term adjustment still distinguishes matching names. One best passage per conversation appears in Smart matches; all exact message matches remain available separately by word. These are ranking heuristics, not general language-model reasoning or guaranteed recall.

Text and validated embedding caches persist locally, with vectors reused only when their embedding text matches the current snapshot. Search results never enter a chat composer. A result carries its URL and source snippet through extension messaging to a fresh tab; its text is not put into the website URL. The content script revalidates the source, reads earlier/scrolling windows if needed, and reuses exact DOM-range navigation. Escape, wheel or pointer interaction cancels the loading scan.

Bulk indexing discovers actual exposed chat links, opens one temporary background tab at a time, captures each readable window, scrolls through history, and closes the tab. It never uses undocumented API endpoints. The website still makes its ordinary page requests. The original tabs, branches and drafts remain untouched. Each scan has a 45-second bound, with honest partial coverage.

Version 1.5.1 applies the same meaning-first weights to in-thread search and the library. A small dictionary normalizes common English spelling variants for the query encoder (for example recognisable → recognizable); source text, visible queries and exact-word tags stay unchanged. Actual ChatGPT render-failure markers and their historical English placeholder text are excluded as answer sources. No new inference service or model is introduced.

Version 1.5.2 adds a soft specificity adjustment to semantic answer scores: `min(1, sqrt(content-term count / 16))`. Very short answer fragments can otherwise borrow relevance from the prompt prepended to their embedding and outrank the remembered input. This adjustment favors substantive passages over generic transitions while retaining short answers with strong similarity. It does not change prompt scores, literal score components, or exact-word groups. A live ChatGPT case exposed this after previously unavailable answers loaded. After the 1.5.2 reload, all six unchanged actual-chat queries ranked their intended passage first and jumped to its exact text, including the confused input. This small check is not a general accuracy guarantee or live verification of cross-chat library selection.

## 1.6.4 passage retrieval correction

The mixed-event compatibility chat exposed representation dilution: the old sentence encoder combined a kitchen accident, luggage preparation and prompt instructions. Its kitchen and boat paraphrases fell below the old model's relevance floor. Indexing independently meaningful verbatim passages, removing inherited prompt text and using a retrieval-trained encoder correct these causes. The old answer-length penalty is removed because answers no longer borrow meaning from prompt prefixes. Word postings still refer exclusively to canonical messages, preserving counts and chronology.

The fixed eight-query regression includes four original queries, four additional paraphrases, competing topics and three unrelated queries. BGE-only retrieval initially placed one additional paraphrase second. The final relative pair-ranking pipeline puts all eight intended passages first on both the CPU check and the three installed-extension browser fixtures. A naive cross-encoder probability blend did not improve the initial set; relative pair ranking also corrects the remembered-input regression exposed by the wider suite. Browser tests click all eight intended results and independently locate the excerpts in original DOM text ranges. This is a bounded regression set, not a general accuracy benchmark. See COMPATIBILITY.md for installed-profile reload and live evidence.
